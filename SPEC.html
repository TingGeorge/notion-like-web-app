§1Scope

§2Architecture

Spec text · ARCH-1 – ARCH-5
ARCH-1

The app is static files served from GitHub Pages.

  • Built with a relative base (base: "./"), so the same build works under /notion-like-web-app/ or at the root of a custom domain (SEC-6).
  • MUST not depend on any server other than api.github.com.
ARCH-2

Routing uses the URL hash (#/…), so GitHub Pages never returns 404 for deep links.

RouteScreen
#/home
#/p/<pageKey>page
#/search?q=search
#/settings/<section>settings
#/setup/<step>setup
#/linklink a device
ARCH-3

All network calls go to https://api.github.com: the REST API and /graphql. The token MUST NOT be sent anywhere else.

ARCH-4

No third-party scripts, fonts or analytics are loaded at runtime. Libraries are bundled at build time.

ARCH-5

Fonts and colours:

  • UI text: -apple-system, BlinkMacSystemFont, "PingFang TC", "Microsoft JhengHei", "Noto Sans TC", "Segoe UI", sans-serif
  • Code: ui-monospace, SFMono-Regular, Menlo, Consolas, monospace
  • Figma uses Noto Sans TC and JetBrains Mono as stand-ins.
  • Colours come from the Figma variables, exported as CSS custom properties (--bg-default, --text-primary, …) with light and dark values.

§3Repository data format

The repo is the source of truth, readable on github.com and by any Markdown tool.

3.1–3.2Pages, folders and names

Try it · title → file name (DATA-4, DATA-5)
Spec text · DATA-1 – DATA-7
DATA-1

A workspace is (owner, repo, branch). The branch is the repo's default branch at setup time.

DATA-2

Every .md file is a page, except files under reserved folders. Non-.md files are ignored and never modified.

  • Reserved: any folder whose name starts with . (e.g. .notes/, .github/), and _assets/ at the root.
  • Because DATA-4 removes leading dots, a title can never produce a . name. A root page whose name would be exactly _assets is written as ＿assets (full-width low line).
DATA-3

A page lives at <dir>/<name>.md. Its children live in the sibling folder <dir>/<name>/. A page with no children has no folder.

A non-reserved folder with no matching <name>.md (common in existing repos, e.g. docs/) is shown as a virtual page: its title is the folder name and it has no body. The file is created only when the user edits that page.

DATA-4

The file name comes from the title:

  • / \ : * ? " < > | are replaced by full-width forms ／ ＼ ： ＊ ？ ＂ ＜ ＞ ｜.
  • Control characters are removed.
  • Leading and trailing spaces and dots are trimmed; an empty result becomes 未命名.
  • Truncated at a character boundary to 150 UTF-8 bytes.
DATA-5

If the file name cannot hold the exact title (DATA-4, DATA-6), the exact title is stored in frontmatter title. Reading: title = frontmatter.title, else the file name without .md.

DATA-6

Names are unique within a folder, compared case-insensitively after Unicode NFC normalisation. On a clash the new name gets (2), (3), … The title itself is unchanged.

DATA-7

Renaming or moving a page renames or moves its .md file and its whole child folder in one commit (SYNC-10).

Spec text · DATA-8 – DATA-10
DATA-8

Frontmatter is YAML. Unknown keys MUST be kept verbatim and in order. Keys the app uses:

KeyMeaning
idULID; stable identity across renames (DATA-9)
titleexact title, only when needed (DATA-5)
iconone emoji
coverroot-relative image path, or gradient:<1-8>
createdISO 8601
DATA-9

Page key:

  • In the app, a page's key is its id, or path:<repo path> while it has none.
  • Files without frontmatter (e.g. created on github.com) are valid. Opening or syncing such a file MUST NOT rewrite it.
  • The app writes id (and created) the first time it saves the page, and also when an action needs a stable id: favouriting, reordering, copying a link, or trashing. This is the only exception to the no-rewrite rule.
DATA-9a

Duplicate ids (a file copied on github.com, 複製頁面, conflict copies):

  • Copies made by the app always get a new ULID.
  • If a pull finds two files with the same id, the file with the lexicographically smaller path keeps it. The other is treated as having no id until next saved, when it gets a new one.
  • Move detection (SYNC-5) ignores ids that appear more than once.
DATA-10

Files are UTF-8 with LF line endings and one trailing newline. The page title is not repeated as a heading in the body.

DATA-14

Editor schema limits: headings and table cells hold inline content only, with no line breaks; code blocks hold plain text; marks are written in a fixed outer-to-inner order.

DATA-15

Markdown the editor does not understand MUST be kept byte-for-byte: raw HTML blocks, footnotes, math, HTML comments other than DATA-12. It is shown as an editable "Markdown" block.

DATA-16

Round trip:

parse(serialize(doc)) = doc   for every doc the editor can produce
serialize(parse(md)) = md   for Markdown written by the app

Other styles (such as * bullets) are normalised only when the user edits that page.

DATA-17

Internal links and attachment paths are root-relative (start with /). github.com resolves those from the repo root, and they keep working when the linking page moves.

  • Percent-encoded in paths: space, %, (, ), <, >, #, ?, [, ]. Everything else, including Chinese, stays as is. Example: /工作/專案%20A.md
  • When a page or folder moves, every link to it or to any page inside it is rewritten in the same commit.
  • Backlinks come from the local index (STORE-4).

3.5Attachments

Spec text · DATA-18 – DATA-20
DATA-18

An uploaded file is stored at _assets/<YYYY>/<MM>/<SHA-256 hex prefix>.<ext>, using the first 8 hex characters. If that path already holds different content, the prefix is lengthened by 4 characters until it is unique. An existing file is never overwritten.

DATA-19

Images longer than 2560 px on the long edge are scaled down before upload, and re-encoded as JPEG quality 0.85 unless they have transparency (then PNG). Any file over 25 MB is rejected with an explanation.

DATA-20

Deleting a page does not delete its attachments. Cleaning up orphans is out of scope for v1.

DATA-22

Trash. .notes/trash/index.json has entries { id, title, originalPath, deletedAt, reason }, where reason is deleted or replaced.

Delete

Moves the file and its child folder to .notes/trash/<id>/ with reason: "deleted".

Conflict loser

A version discarded in a conflict (SYNC-6) is saved the same way with reason: "replaced".

Restore

Moves the files back (DATA-6 if the name is taken).

Removes them from .notes/trash/; they stay in git history. On sync, entries older than trashRetentionDays are removed permanently.

§5Sync

5.1Principles

Spec text · SYNC-1 – SYNC-3
SYNC-1

The remote branch head is the truth. The device keeps the commit it last synced (headSha) plus local changes.

SYNC-2

No text is ever lost. Every version that existed on a device or on GitHub survives somewhere: in the page, in a conflict copy, in the trash (DATA-22) or in git history.

SYNC-3

Only one pull or push runs at a time per device (STORE-6). Before each one, the open editor is flushed into files.text while the sync lock is held.

5.2Pull

Spec text · SYNC-4 – SYNC-5
SYNC-4

A pull runs:

at app startwindow becomes visibleevery 60 s while visiblebefore every pushon 「立即同步」
SYNC-5

Steps:

  1. GET /repos/{o}/{r}/git/ref/heads/{b} with If-None-Match: <etag>. Stop if the response is 304 or the ref equals headSha.
  2. GET /repos/{o}/{r}/git/trees/{treeSha}?recursive=1. If it is truncated, report "repo too large" (out of scope).
  3. Download every page or meta file whose blob SHA differs from baseSha:
    • ≤ 20 files: GET /git/blobs/{sha}, at most 2 at a time; content is base64, decoded with TextDecoder;
    • > 20 files: GraphQL, about 100 blobs per query: object(oid:"…") { ... on Blob { text byteSize isBinary } }.
  4. Apply the changes in this order (below).
  5. Set headSha, treeSha and etag.

Apply order

#ChangeRule
1MovesThe same id at a new path, outside .notes/trash/ and not duplicated (DATA-9a), is a move. Local edits are applied to the new path by three-way merge.
2Moves into trashMoves into .notes/trash/ count as deletes (rule 3).
3DeletesA remote delete of a clean local file deletes it locally. If the local file is dirty, the local version is kept and re-created by the next push, with the notice 「這一頁在另一台裝置被刪除，但這台裝置有修改，所以保留了。」
4EditsClean locally: take the remote text. Dirty locally: three-way merge by line (node-diff3), base = baseText, ours = text, theirs = remote. Frontmatter merges key by key, the body by line. A clean merge sets text = merged and baseText = remote. Overlaps go to SYNC-6.
5AddsA new remote path is added locally. If an unpushed local page already uses that path, the local page is renamed per DATA-6 first.
6Local move/delete vs remote editLocal move + remote edit at the old path: the remote edit is merged into the moved file, matched by id. Local delete + remote edit: the remote text goes into the local trash entry, with the notice 「你刪除的頁面在另一台裝置有新的修改，已一起放進垃圾桶。」

Open editors

Pages open in this or another tab (BroadcastChannel) show the new content right away. A clean page has its editor content replaced; a dirty page gets the merge result applied the same way. In both cases the cursor stays at the same block and offset.

Rename or move · SYNC-10

One local operation, one push: 「移動「專案 A」到「工作」」. Covers the page file, every file in its folder, inbound links and settings.json.

Spec text · SYNC-7 – SYNC-10
SYNC-7

Triggers and throttling:

  • A push runs 5 s after the last edit, but at most once every 30 s.
  • It also runs when leaving a page, when the app is hidden (best effort) and on 「立即同步」. These ignore the 30 s spacing.
  • A page whose title and body are both empty is never pushed.
  • When 「自動同步」 is off, there are no automatic pushes at all (timer, leave, hide). Only 「立即同步」 pushes. Pulls keep running.
SYNC-8

Steps (Git Data API, one commit per push):

  1. Pull (SYNC-5), so the base is the current head.
  2. For each dirty file, record the exact text being pushed in pushing.
  3. Upload each new attachment from uploads: POST /git/blobs (base64).
  4. POST /git/trees with base_tree = the head tree:
    • an entry with inline content for each changed text file;
    • an entry with the blob SHA for each attachment;
    • an entry with sha: null for each deletion, only for paths that exist in the head tree from step 1. A deleted local file whose path is not in that tree is marked clean without a tree entry.
  5. POST /git/commits with parents: [headSha].
  6. PATCH /git/refs/heads/{b} with force: false. On 422 or 409, go back to step 1. After 3 failed attempts, show the Error state.
  7. On success, for each pushed file: set baseText = pushing; compute baseSha locally; clear pushing (the file stays dirty if text ≠ pushing). Then set headSha and delete the pushed uploads rows.
baseSha = SHA-1( "blob " ‖ len ‖ "\0" ‖ bytes )   via WebCrypto

SYNC-12

Network failures retry with exponential backoff (5 s → 5 min), and immediately on the browser online event.

SYNC-13

Rate limits (GitHub REST best practices):

  • The app reads x-ratelimit-remaining. Below 200, polling (SYNC-4) stops until x-ratelimit-reset.
  • Secondary limit (403 or 429): wait for retry-after if present; otherwise wait 60 s, then back off exponentially.
  • Requests are made serially, except the 2-way blob downloads in SYNC-5.
  • SYNC-7's spacing keeps content-creating requests (three per push) under GitHub's 500 per hour: timed pushes come at most 120 times an hour, so at most 360 such requests.
SYNC-14

Limits for v1: up to 5,000 pages, 1 MB per page, 25 MB per attachment. Above these the app warns and keeps working where it can.

5.6Page history (D06 / M18)

Spec text · SYNC-15 – SYNC-16
SYNC-15

Versions come from GET /repos/{o}/{r}/commits?path=<path>&per_page=30, paged. Each row shows date, time and the Device: trailer.

  • The preview loads GET /repos/{o}/{r}/contents/<path>?ref=<sha> with Accept: application/vnd.github.raw, which also works for files over 1 MB.
  • 「還原這個版本」 replaces the local text with that version as a normal edit.
SYNC-16

6.5Link a new device

Spec text · LINK-1 – LINK-4
LINK-1

Payload and encryption:

  • An 8-character pairing code from the alphabet 23456789ABCDEFGHJKMNPQRSTUVWXYZ, shown as XXXX-XXXX.
  • Payload ghnotes:1:<salt>.<iv>.<ciphertext>, all base64url.
  • Ciphertext: AES-GCM of the UTF-8 JSON {"o","r","b","t","e"} (owner, repo, branch, token, tokenExpiresOn).
  • Key: PBKDF2-SHA-256 of the pairing code, 600,000 iterations, 16-byte salt.
  • QR error correction is level M.
LINK-2

Source device: 設定 → 連結新裝置 → 「顯示 QR code」.

  • The QR code and pairing code appear only after that click.
  • Both hide after 60 s and when the window is hidden. 「重新產生」 makes a new salt and code.
  • 「複製設定碼」 copies the same encrypted payload as text, with a warning that clipboard history and Universal Clipboard can keep it.
LINK-3

New device: 「用 QR code 從另一台裝置連結」 opens the camera (getUserMedia, rear camera, M15). Frames are decoded with jsQR.

  1. A ghnotes:1: payload leads to M22, where the user enters the pairing code.
  2. After decryption, M22 shows the owner, repo, GitHub login (GET /user) and expiry date, and asks for confirmation.
  3. SETUP-8's write probe runs, then the app goes to D14/M14.

Any other QR content shows 「這不是 GitHub Notes 的 QR code」. Three wrong pairing codes in a row discard the scanned payload.

LINK-4

Spec text · SEC-1 – SEC-8
SEC-1

Token scope. The UI and docs tell users to create a fine-grained token with only the notes repo, Contents: Read and write, and an expiry date.

SEC-2

The token is used only in the Authorization header of requests to https://api.github.com. It MUST NOT appear in URLs, logs, error reports, exports or the service-worker cache.

SEC-3

The Content Security Policy is set with a <meta> tag, because GitHub Pages cannot set headers. <meta> cannot carry frame-ancestors, so the app also refuses to run inside a frame (if (top !== self)).

default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' blob: data: https:; connect-src 'self' https://api.github.com;
worker-src 'self' blob:; media-src 'self' blob: mediastream:;
object-src 'none'; base-uri 'self'; form-action 'none'
SEC-4

HTML inside Markdown is sanitised with DOMPurify (bundled) before rendering. Everything else is shown as text. Allowed:

  • elements: details, summary, span (data-color and data-bg only), u, br, kbd, sub, sup;
  • link URLs: http(s):, mailto: and root-relative paths;
  • image URLs: /_assets/…, blob: and https:.
SEC-5

Attachments are fetched into blob: URLs. Images render only through <img>. Any other file, including .html and .svg, is offered only as a download (<a download> with type application/octet-stream). The app never navigates to a blob: URL.

SEC-6
Known risk, accepted by the owner. GitHub Pages serves all of an account's project sites from one origin (tinggeorge.github.io), so another Pages site of that account can read this app's storage.
  • Mitigation: keep other Pages sites free of third-party code.
  • Before inviting other people, give this repo its own custom domain (e.g. notes.example.com). A custom domain on the user site would be inherited by every project site and isolates nothing.
  • Thanks to ARCH-1 the build works at any path. Local data does not move to the new origin, so every device syncs, then sets up again.
SEC-7

Token sharing:

  • QR linking copies the same token to every device, so revoking it on github.com locks all of them. Each device then needs 更換 token, or a fresh QR link from a device that already has the new token.
  • Users who prefer separate tokens per device can skip QR linking and paste a different token on each device.
  • A lost device: revoke the token. The notes remain in the repo.
SEC-8

The QR code and the setup code are encrypted with the pairing code (LINK-1); neither alone reveals the token. The new device always shows which account and repo it is about to link to (LINK-3), so a planted QR code cannot silently point it at someone else's repo.
